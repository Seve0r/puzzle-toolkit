# 编码识别的坑与解法

一串可疑文本，先别手写 `base64 -d`。判断"这属于哪种编码"比解码本身难得多，
`scripts/codec.py` 把常见格式的**结构特征**都编进去了。

```bash
C=~/.dsh/skills/codec-toolkit/scripts/codec.py

python3 $C auto 'S1VWRVIgTEFOR1VBR0U='     # 自动识别 + 递归剥皮
python3 $C brute 'aGVsbG8gd29ybGQ='        # 所有编码全试一遍，按可读性排序
python3 $C dec base58 '2NEpo7TZRRrLZSi2U'  # 指定编码解码
python3 $C grid '322T332T36363A312T'       # 矩阵重排：各种行/列/蛇形读法
python3 $C enc hex -f some.bin             # 文件输入（二进制安全）
python3 $C list                            # 看支持哪些名字
```

`auto` 会打印**解码路径**（如 `url → base64`），多层嵌套也能剥。`-q` 只输出结果：
它压的是「解释」（解码路径、损失率、用了哪对编码、`--deep` 的层级），
但**失败原因照常输出**——否则加了 `-q` 就再也看不到「为什么解不出」。

## 支持的编码

Base16/32/32hex/58/62/64/64url/85/91、hex、二进制、十进制、八进制、
URL、HTML 实体、Unicode 转义（`\u`/`\U`/`\x`/`U+XXXX`）、Quoted-Printable、ROT13/ROT47/Atbash、
摩斯、盲文（含 8 点原始位串 `dec braillebits`）、gzip/zlib/bz2 内嵌流、
UTF-16、**UTF-32**（`utf32` 自动判字节序 / `utf32be` / `utf32le`）、GBK、
**mojibake**（乱码还原：UTF-8 被误读成 GBK，以及中日韩编码互相误读，见下方第 ⑦ 条）。

## 「字符编码 × 进制」自己指定（`convert`）

现有的 `dec` / `bin` / `hex` / `oct` / `block36` 其实都是「某个进制 + **UTF-8**」
的快捷方式——字符编码那一半写死了。同一批字节如果其实是 GBK，用它们解出来的
是另一句话（或者乱码），而工具不会提醒你。

`convert` 把这两个维度拆开：

```bash
codec convert '228 189 160' -r 10          # 你（自动判字符编码）
codec convert 'E4BDA0'      -r 16          # 你
codec convert '344 275 240' -r 8           # 你
codec convert '11100100…'   -r 2           # 你
codec convert '6F4M576D583K6F4A3O6H424L6D3W49' -r 36   # 离开的钥匙

# 同一批字节，换个字符编码就是另一句话
codec convert 'C0EB' -r 16                 # 离（auto 试出 GB 系）
codec convert 'C0EB' -r 16 -e big5         # 燭

# 显式指定，失败会明说
codec convert 'E4BDA0' -r 16 -e gbk
# 失败：这些字节不是合法的 gbk：can't decode byte 0xa0 in position 2

# 解析阶段的报错会点名具体字符，不是含糊地说「位数不对」
codec convert '41g 42' -r 16
# 失败：含十六进制以外的字符：'g'
codec convert '01000001x01000010' -r 2
# 失败：含二进制以外的字符：'x'      （不会静默吞掉 x 就解出 AB）
codec convert '2W333' -r 36
# 失败：base36 位数是奇数（5），每两位表示一个字节
```

| 选项 | 取值 |
|---|---|
| `-e`, `--encoding` | `auto` / `utf-8` / `gbk` / `gb18030` / `big5` / `shift_jis` / `ascii` / `latin-1` |
| `-r`, `--radix` | `16` / `10` / `8` / `2` / `36` |

### `auto` 是「我挑一个」，不是「它就是这个」

最容易被误读的一处，实测被你抓到过：`2W33342T` 用 `convert` 解，报告写
`utf-8`；用 `auto` 解，报告写 `ASCII`——而这批字节当年是按 **GB18030** 读的。

三种说法**全都不算错**：解出来是 `hope`，四个字节全 < 128，在 utf-8 / gbk /
gb18030 / big5 / shift_jis / ascii / latin-1 **七种编码下逐字节相同**。纯
ASCII 时压根不存在「是哪种编码」这个问题。

所以报告现在分三种写法：

| 情形 | 报告 |
|---|---|
| 纯 ASCII | `ASCII（与编码无关）`，并列出哪些编码解出来一样 |
| 只有一种编码能完整解出 | 直接写那个编码名 |
| 多种都能解，且**解出不同的通顺文字** | 主选照写，另附候选清单 |

判断"通顺"用常用字占比（`_common_ratio`），低于主选六成的不列——GB 系的字节
常常同时是合法 Big5，会附赠一串纯属巧合的胡话（`离` 的字节按 Big5 读成
`燭`），把胡话摆成平等候选等于逼用户做一次无意义的判断。

**已知当年用的编码时，永远优先 `-e` 显式指定。** 工具的"猜"原理只是「哪个能
完整解出」，而 `latin-1` 恒真、GB 系覆盖极广——猜对不等于猜准。

界面上它就是编码页下拉栏里的一项「编码×进制（自己指定）」，两个下拉框选完即可。

**位宽是自动的**：定宽进制（16 两位、2 八位、36 两位）直接切，空格可有可无；
变长进制（10 / 8）必须有分隔符，否则 `111` 分不清是一个数还是三个数。

`--encoding auto` 会按 `utf-8 → gbk → gb18030 → big5 → shift_jis → ascii`
依次试，**要求整个字节流合法**（不做替换），全都不行才退到 `latin-1` 并明确
警告「解出来多半是乱码，更可能是原始字节已经损坏」——比闷头猜结果强。

`latin-1` 特意**不算候选**：它对任意字节流都合法（逐字节映射到 U+0000–U+00FF），
恒真所以毫无信息量。放进候选里，任何乱码都会显示"同时合法于 latin-1"，提示
立刻变噪音。

## 这四种「进制编码」怎么选

名字只体现「数怎么表示」，而**真正决定选哪个的是怎么切成字节**——这点从
进制名上看不出来，是最容易卡住的地方：

| 输入长这样 | 选 | 切法 |
|---|---|---|
| `65 32 87 72` | **`decimal`** | 每个数 = 一个字节，**必须**有分隔符 |
| `11100111 10100110` | **`binary`** | 8 位 = 一字节，空白可有可无 |
| `4132 4157` 或 `41324157` | **`hex`** | 2 位 = 一字节，空白可有可无 |
| `101 40 127` | **`octal`** | 每个数 = 一个字节，必须分隔 |

规律：`hex` / `binary` 是**固定位宽**（2 位 / 8 位一字节），所以空格只是给人看的，
去掉也照样解；`decimal` / `octal` 是**一串独立的数**，没有分隔符就分不清
`111` 是一个数还是三个数。

位宽不对就**报错，不补零**：`dec hex 61626` 提示「十六进制位数是奇数（5）」，
`dec bin 0100000` 提示「二进制位数 7 不是 8 的倍数」。左边补零等于替你猜了一个
字节，猜错还会静默改掉数值——少打一位和本来就是这样，事后完全分不出来。

`dec bin` 也**不会**删掉末尾的 `\x00`：NUL 在位流、隐写载荷里是正常数据，
`dec bin "01000001 00000000"` 解出的是**两个字节**，不是单个 `A`。

所有 base 系列（64 / 32 / 58 / 85 / 91）解码前都会先去掉空白，所以从网页、
聊天记录里复制出来的折行密文可以直接贴。

### ★ `base36` 与 `block36` 是两回事

名字像，语义完全不同，而且**解出来一个是垃圾一个是正文**：

| | 怎么算 | `6F4M576D583K…` 解出 |
|---|---|---|
| `base36` | 把**整串**当一个大整数，再转字节 | 乱码 |
| `block36` | 每**两位**独立转一个字节（`6F`=231=`E7`、`4M`=166=`A6`…） | `离开的钥匙` |

谜题里那种「看着像 hex、却掺了 `M`/`K`/`O`/`W`」的串多半是 `block36`——
A-F 以外的字母说明它不是十六进制，而两位一组恰好落在 0–255 说明它在按字节分组。

```bash
python3 codec.py dec block36 '6F4M576D583K6F4A3O6H424L6D3W49'   # 离开的钥匙
python3 codec.py enc block36 '离开的钥匙'                          # 6F4M576D…
```

### ★ 零宽字符会让识别全盘失配

从网页、PDF、聊天记录里复制的数据，常常夹带 **U+200B/200C/200D/FEFF**（零宽
空格、零宽不连字…）。它们肉眼不可见，但足以让所有「按字符集匹配」的规则失配——
表现为「明明该是 hex/base36，`auto` 却说没有可靠路径，还给一个 mojibake 提示」。

`auto` 和 `convert` 都会先按原串试，不行再剥掉零宽字符重试，而且**会报出剥了
几个**：

```
[注意] 原文含 40 个零宽字符（U+200B/200C/200D/FEFF），已剥离后再解
       ——若是刻意藏的，请另行处理
```

不静默剥的原因是：零宽字符也可能是**真隐写**（把信息藏在不可见字符里），闷头
去掉就等于丢线索。工具只负责报数，判断交给你。

来源方面，**B 站的富文本编辑器会自动插入 U+200C 防断行**——从简介/动态复制
数据时几乎必然带进来。这类是噪音，剥掉就行。

自查：`[hex(ord(c)) for c in s]` 里出现 `0x200b`/`0x200c`/`0x200d`/`0xfeff` 就是它。

### ★ `ascii85` 和 ASCII 是两回事

最容易混的一对名字：

| 名字 | 是什么 | 例 |
|---|---|---|
| **ASCII** | 字符**编码**（7 位，0–127），规定「A = 65」 | `65 32 87` → `A W`（用 `dec`） |
| **ASCII85 / Base85** | 传输**编码**，把二进制压成可打印字符（像 base64） | `Hello World` ↔ `87cURD]i,"Ebo7` |

ASCII85 名字里的 "ascii" 指的是「**输出**的是 ASCII 字符」，不是「字符集是
ASCII」——就像 Base64 里的 base 跟数据库没关系。所以 `65 32 87` 拿 ascii85 解
只会得到乱码，它该用 `dec`。

### 报告里的「输出编码」怎么读

`auto` 解出来后会报三样：`路径 / 得分 / 输出编码`。后两者容易误解：

- **路径** = 用什么编码把输入还原成**字节**（`dec` / `base32` / `mojibake` …）
- **输出编码** = 那堆字节又按什么编码变成**文本**

输出编码分三种，因为 ASCII 是 UTF-8 的子集，0–127 的字节两者逐字节相同：

| 报告 | 含义 |
|---|---|
| `ASCII` | 结果全是 0–127，说 ASCII 更准确 |
| `UTF-8` | 含非 ASCII 字符，只能是多字节编码 |
| `UTF-8（有替换符，字节非法）` | 结果里有 `�`，说明原始字节不是合法 UTF-8——这是数据问题，不是选错编码 |

### ★ 别和 `num.py` 混

同一句「255 转成十六进制」在两处意思完全不同：

| 你想要的 | 用哪个 | 为什么 |
|---|---|---|
| `255` → `ff`（**一个数**换种写法） | `num.py 255 --to 16` | 数值转换 |
| `72 101 108 108 111` → `Hello`（**一列数**变成字节） | `codec dec dec '72 101 108 108 111'` | 字节流解码 |

所以 `codec dec bin` **不是**「把数换成二进制」，而是「一串 0/1 按 8 位一组
变成字节，再解成文本」。判据很简单：**结果是文本 → 用 codec；结果还是个数 → 用 num.py**。

## 编码方向（`enc`）

`dec <编码> <文本>` 是解码，`enc <编码> <文本>` 是编码，同一张表：

```bash
python3 codec.py enc b64 Hello       # SGVsbG8=
python3 codec.py enc hex Hi          # 4869
python3 codec.py enc wabun じんこう   # --.-./../.-.-./----/..-（和文摩尔斯）
```

**双向的 35 个**（共 37 个编码概念，其余只有解码，见下）：base16/32/32hex/58/62/64/64url/85/91、
bin、dec、oct、url、html、unicode、qp、rot13/rot47、atbash、morse、**wabun**、
braille、utf16/be/le、utf32/be/le、js、uu、gzip/zlib/bz2、punycode、gbk。

### 有几种编码的输出是二进制

`utf16` / `utf32` / `uu` / `gzip` 编码后的东西**不是可读文本**——codec 统一
用 latin-1 承载（1 字符 = 1 字节），所以直接看是乱码。正常用法是接一层：

```bash
python3 codec.py enc gzip "要压缩的内容" | python3 codec.py enc b64    # 可复制
python3 codec.py enc utf16be "Hello" | python3 codec.py enc hex        # 十六进制
```

反过来解码也认这两种：`dec gzip` 和 `dec utf16` 内部走 `raw_bytes()`，
会先判断输入是不是 latin-1 承载的字节流。

### 只有解码方向的

`braillebits`（8 点原始位串，输出是多视图，没有唯一反向）。

### 需要额外参数的反向

`mojibake` 和 `convert` 也有反向，但光给文本不够——还得知道**编码对**或
**字符编码**：

```bash
codec.py enc mojibake 'テスト用の文字列' --from gbk --to shift_jis
# → 僥僗僩梡偺暥帤楍        （原文按 shift_jis 编码，再按 gbk 解）

codec.py enc convert '编码测试' -r 16 -e utf-8
# → e7bc96e7a081e6b58be8af95    （换 -e gbk 就是另一串：8 字节）
```

所以它们不进 `ENCODERS` 注册表（表里的编码器只接一个字符串），而是
`main()` 里的独立分支，`codec list` 也统计不到。

**反向为什么有用**：解出一串东西后，最硬的判据不是「看起来像中文」，而是
「按我猜的编码对能不能把它造回原样」。造不回去，说明猜错了。

`mojibake` 的反向早先是故意不做的（怕「制造乱码」被误用），但验证需求更实际。

### 自反的两个

`atbash` 和 `rot47` 解两次回到原文，所以 `enc` 和 `dec` 是同一个函数。

## mojibake：`缂栫爜娴嬭瘯` → `编码测试`

UTF-8 的中文被当成 GBK 读了一遍，是 ARG 里最常见的乱码。还原方向反直觉：
**先 `encode('gbk')` 拿回原始字节，再 `decode('utf-8')`**。

`dec mojibake` 会枚举 gb18030/gbk/big5/shift_jis/euc-kr/latin-1 等假设，
各自反编码回字节再按 UTF-8 解，**取 U+FFFD 损失率最低的那个**——
猜中时无损，猜错时字节流不合法会碎成大量替换字符。

损失率本身就是信号：

- **0%** → 数据完整，还原可信
- **>2%** → 直接报错，说明原始字节流本身就缺字节

第二种情况不能用「猜个最像的」硬输出。比如 `濡備綍杩涘叆寮備笘鐣出殑闂紵`
最好假设也损失 30.8%，还原成 `如何进入异世畳���闼�`——后半段是猜的，
当成答案会误导。**要回头找更原始的来源。**

`codec.py mojibake_rank(s)` 可以直接看到所有假设的损失率排名，用来判断数据坏在哪。

### 第三类乱码：整串都是西欧字符（`²âÊÔ` → `测试`）—— **默认关闭**

> 这一类的自动还原已经写好，但目前 `_ENABLE_LATIN1_MOJIBAKE = False`。
> 误伤风险还没摸清（见 `TODO.md`），先不放进主线。
> 应急时显式指定编码对仍然可用：
> `dec mojibake '²âÊÔ' --from latin-1 --to gbk`

文件名、压缩包目录里最常见：GBK 字节被当 **Latin-1 / CP1252** 显示。

```bash
$ codec.py dec mojibake '²âÊÔ'
  [西欧字符] 按 cp1252 编回字节、按 gb18030 解（可读度 100%）
测试
$ codec.py dec mojibake 'ÎÄ¼þÃû×Ö.txt'
文件名字.txt
```

它和前两类**互不重叠**，判据也完全不同：

| | 输入端长什么样 | 前提 |
|---|---|---|
| UTF-8 被当 GBK | `缂栫爜`（汉字乱码） | 原文以汉字为主 |
| 中日韩互读 | `僥僗僩梡`（汉字乱码） | 原文以汉字为主 |
| **字节被当西欧码** | `²âÊÔ`（**西欧字母**） | 原文全在 Latin-1 范围 |

最后这类一个汉字都没有，前两类的门槛直接把它挡在门外，所以是单独一条路。

**必须先做 NFC 规范化**：macOS 和不少工具按 **NFD** 存文件名，把 `Ï`(U+00CF)
拆成 `I`(U+0049) + `\u0308`（组合分音符）。视觉上完全一样，但 `\u0308` 在任何
单字节编码里都编不出来，于是还原在**第一步**就失败，报
`'latin-1' codec can't encode character '\u0308'`——一个字节都没处理。
`_encode_back()` 和这一类都先 `unicodedata.normalize("NFC", s)` 再动手。

复制粘贴时看不出来，判断办法：`[hex(ord(c)) for c in s]`，出现 `0x308`、
`0x3099`（浊点）这类就是 NFD 形式。

**防假阳性**靠「高位字符占比」：真正的乱码是**成串**的（GBK 一个汉字 = 两个高位字符），
而正常西欧文本只有零星变音字母。少了这道门槛，`Müller` → `M黮ler`、
`Señor` → `Se隳r`、`© 2026` → `ｩ 2026` 都会被"解"出来，比原文更糟。

**排序用 `_common_ratio` 而不是 `_plain`**：`b'\xb2\xe2\xca\xd4'` 按 euc-kr 能解出
`꿎桿`，`_plain` 给满分（韩文都算可打印），但 `_common_ratio` 是 0——用 `_plain`
排序会让韩文赢过正确的「测试」。

### 第二类乱码：中日韩编码互相误读

上面那套只假设「**目标是 UTF-8**」，覆盖不了另一大类：**GBK 文本被当成
Shift_JIS 读**（或反过来）。这类乱码用 UTF-8 是彻底解不出来的——字节流在
UTF-8 眼里全是非法序列，只会碎成一堆 `?`。

典型：

```
僥僗僩梡偺暥帤楍  →  テスト用の文字列
```

方向是 `encode('gbk')` 拿回字节，再 `decode('shift_jis')`。

`dec mojibake` 会自动进入二级：把「源编码 × 目标编码」全组合试一遍，
判据换成**「结果是否显著更像正常文字」**（不是损失率，因为很多组合都能
0 损失但产出一堆垃圾）。命中时会打一行 `[跨编码]` 说明用了哪一对。

四个防假阳性的门槛（实测踩出来的，缺一个就乱转）：

| 门槛 | 作用 | 不设的后果 |
|---|---|---|
| 原文以 **CJK 汉字**为主（≥50%） | GB18030 是全 Unicode 覆盖，任何文本都能被它编回字节 | 俄文 `Русский текст` 被"翻译"成 `妓批扼扼抗我抄` |
| 结果可读度 **≥0.85** | 挡住私用区/控制符/生僻字 | `锟斤拷` 被解成韩文 `占쏙옙` |
| 可读度**提升 ≥0.4** | 已经是正常文字的不再改 | 正常中文被反复误转 |
| 长度 **≥3** | 单字字节碰巧合法 | `茻` → `踈` |

「可读度」= 汉字看是否 GB2312 或 Shift_JIS 收录（日文新字体 `実`/`嘘`
在 GB2312 里没有，只看 GB2312 会把它们当成乱码特征），假名算好，
半角片假名、私用区、控制符算坏。

### 已知编码对就直接指定：`--from` / `--to`

> 界面上这两个是**下拉框**（选项取自 codec 自己的清单，`MOJIBAKE_ENCODINGS`
> 和 `MOJIBAKE_TARGETS`），不用手打编码名。第一项「不指定」= 走自动判断。
> 下拉选项是 `import codec` 现取的，codec 里加编码界面自动跟着有，不会分叉。

自动认不出、或你已知作者用的编码时，别让它猜：

```bash
python3 codec.py dec mojibake --from gbk --to shift_jis '僥僗僩梡偺暥帤楍'
# テスト用の文字列
```

含义是「这段文字原本是按 `<源>` 编成字节的，被当 `<目标>` 解了」。只给一侧
时另一侧取默认（源 `gb18030`、目标 `utf-8`），并在 stderr 说清用了默认值。
这条路不做任何猜测，结果可复现。

### 单字/双字不要用 `dec mojibake`

一两个字符不足以下结论，字节碰巧合法就会给出误导性结果（`茻` → `踈`、
`あいうえお` → `ƦƨƪƬƮ`）。工具现在会直接拒绝短于 3 字符的输入——
真实的乱码是被系统性误读的产物，必然成串出现。

### 数据半路丢了字节：`�` 分段还原

谜题数据常常不是编码错位，而是**真丢了几个字节**——从网页复制、OCR、
聊天记录转存都会这样，缺失处变成 `�`（U+FFFD）。

这种输入以前是死路：U+FFFD 不在任何编码里，整段 `encode()` 直接抛异常，
所有假设被跳过，工具只能说「数据损坏」。**但缺失处两侧的字节是完好的**，
切段分别还原就能把能救的全救回来：

```
输入：崱傑偱慡偰� 偺壧偲夋柺偼堄枴偑偁� 傞丅恀幚偑柧傜偐偵…
输出：今まで全て� の歌と画面は意味があ� る。真実が明らかにな…
--best：今まで全て? の歌と画面は意味があ? る。真実が明らかにな…
```

`--best` 会把 `�` 显示成 `?`（更好读）。工具会报告「原文 N 处字节缺失、
成功还原 M/M 段」。

- **编码对统一**：取「能把最多段解成正常文字」的那一对，而不是逐段各自猜——
  同一段乱码本来自同一对编码，逐段独立猜会拼出互相矛盾的版本。
- **准入门槛**：原文得「像中日韩乱码」（CJK 汉字占多数）而**不是本来就正常**。
  不设这条的话，`正常中文�乱码` 会被转成 `攣끽櫓匡�쫘쯤`、`今まで全て� の歌`
  会被转成 `書まで畠て� の梧`——分段后每段只有两三个字，假阳性特别容易。
- `--from gbk --to shift_jis` 遇到 `�` 也会自动分段，不会因为编不回去而失败。

### 多层乱码 + 中间才丢字节：`--deep` 自动分段

上一节是**一开始就带 `�`**。还有一种更隐蔽：输入看起来完全正常，
解完**第一层**才出现 `�`——丢字节发生在某一轮回编码/解码当中。

这类数据要解多层，但中间层的 `�` 是个陷阱：`gb18030` 给 U+FFFD 也留了
编码位（`84 31 a4 37`），整段编回去会把这个「此处无数据」的标记当成
4 个真实字节解出来，在正确答案后面拖一条垃圾尾巴。

```
输入：郛よｫ辷懷ｴ螫ｭ逖ｯ
--deep 80（修复前）：编码??试幄1?7     ← 尾巴是垃圾
--deep 80（修复后）：编码??试         ← 正确
```

现在 `--deep` 每层都会检查：一旦出现 U+FFFD 就按它切段，各段分别继续
还原，丢失位置原样保留。

### 粘贴带进来的换行

从网页或聊天记录复制乱码时，末尾很容易多一个换行或空格。显式编码对
（`--from A --to B`）是逐字节对齐的，多 1 个字节后果差别很大：

| 字节数 | 报错 | 看起来像 |
|---|---|---|
| 38 | `unexpected end of data` | 数据在结尾被截断 |
| 39（多一个 `\n`） | `invalid continuation byte` | 数据损坏 |

后者很容易把人引向「数据坏了」，实际只是多粘贴了一个换行。
现在 mojibake 的所有入口都会自动去掉首尾 **ASCII** 空白
（全角空格 U+3000 不动，它在乱码里可能是真数据）。

### `€` 与私用区字符：乱码里的「半个字节」

UTF-8 中文 3 字节、GBK 汉字 2 字节，两者不对齐，所以乱码里经常出现**孤立的
半个字节**。这类字节在 CP936 里是这么表示的：

| 原字节 | 乱码里看到的字符 | 说明 |
|---|---|---|
| `0x80` | `€`（U+20AC） | CP936 把单字节 0x80 定义成欧元符号 |
| 用户自定义区双字节 | U+E000–U+F8FF 私用区字符 | 如 `\ue043` 对应字节 `AA E4` |

私用区字符交给 `encode('gb18030')` 能正确还原成原始字节，**但 `€` 不行**：
`gb18030` 把 U+20AC 编成双字节 `A2E3`，凭空多出一个字节，导致它之后的内容
整行错位一格。所以 GBK 系回编码必须手动把 `€` 还原成 `0x80`（代码里是
`_encode_back()`）。

不处理时症状很典型：本来能无损还原的一行，解出来是「居民为什么不购入
**丢?个**亲生孩子」——正确的「一个」被吃掉，损失率还被抬到 5.3%，
反而把正确假设挤掉了。

### 多层乱码：`--deep`

乱码可能套了好几层。`--deep [N]` 会反复还原，直到「正常文字占比」达到 N%
（0~100，默认 50）：

```bash
python3 codec.py dec mojibake --deep -f 原文.txt      # 默认阈值 50
python3 codec.py dec mojibake --deep 85 -f 原文.txt   # 解得更彻底
```

它逐层打印损失率和可读率，标出采信第几层。「正常文字占比」= 汉字看是否
GB2312 常用、假名算正常（ASCII 不算，否则解过头的 ASCII 噪音会被算成高可读率）。

跨编码那一级也会参与，所以 `--deep` 对 `僥僗僩梡偺暥帤楍` 这类同样一步到位。

**可读率不是单调的**：一串双层乱码实测是 33.7% → 36.4% → 88.5% → 0%，
所以取的是全局最高那层而不是最后那层，解过头会自动退回。

**局限**：只对「整段层数一致」的乱码有效。如果同一行里有的部分已经解开、
有的还没有（混合层数），自动递归会把已解好的部分重新弄坏——这种情况必须
手工切段，分别用 `--best` 处理。


## Punycode：`XN--28JM5B5A8K5K8CRA` → `これはテストです`

把非 ASCII 文本塞进纯 ASCII 域名的编码，IDN（`.jp` 的日文域名那种）就用它。
固定带 `xn--` 前缀，属于**可逆编码**，性质接近 Base64 而不是加密。

```bash
python3 codec.py dec punycode 'XN--28JM5B5A8K5K8CRA'   # これはテストです
python3 codec.py dec punycode -f 四条.txt              # 多行批量，一段一行输出
python3 codec.py enc punycode 'これはテストです'         # xn--28jm5b5a8k5k8cra
```

`auto` 会自动认出 `xn--` 前缀。

**两个坑**：

1. **不能用 `idna` codec 解**。`idna` 会当成完整域名做校验，谜题数据里带逗号
   （例如 `XN--,-47TL2MZE6MYDZA3P` 这种带逗号的）或空格就一律报错。
   必须剥掉前缀后直接走 `punycode` codec。
2. **必须抢在 base64url 前面**。这类串长度常是 4 的倍数、字符集又落在
   base64url 里（`-` 是合法字符），不优先识别就会被 base64url 抢走，解出乱码。

样例（注意 `xn--` 前缀大小写不影响识别，但**必须保留**）：

| Punycode | 明文 |
|---|---|
| `XN--28JM5B5A8K5K8CRA` | これはテストです |
| `XN--28J2A3AR1P` | こんにちは |
| `XN--L8JIR6I4G` | ありがとう |
| `XN--VCK8CUC4A2869A6ULUZQ` | サンプル文字列 |


## 和文モールス（`dec wabun`）

日文假名用的摩斯体系（和文モールス符号 / Wabun code），**和国际摩斯是两套
完全不同的表**：同一个符号在两边代表不同字符。`....` 在国际是 `H`，
在和文是 `ヌ`。所以必须显式指定用哪套：

```bash
python3 codec.py dec wabun '--.-./../.-.-./----/..-/..--/'   # 和文
python3 codec.py dec morse '.... . .-.. .-.. ---'             # 国际
```

`auto` 会自动分辨：**只要有一段码在国际表里查不到，就判定为和文**
（`--.-.` 这种国际根本没有）；全部能按国际解释时优先国际。

### ★ 表源与校对（抄错一次，错得"像真的"）

表按 **無線局運用規則 第十二条 別表第一号** 编写
（转录参考：[モールス符号一覧](https://www.benricho.org/symbol/morse.html)）。

2026-10 逐项核对时修掉四处抄错。这类错误特别毒，因为**错出来的码也是合法的**：

| 字符 | 当时写错 | 正确 |
|---|---|---|
| キ | `-..-..` | `-.-..` |
| ト | `..-`（和 ウ 撞码） | `..-..` |
| （ | `-.--.`（和 ル 撞码） | `-.--.-` |
| 」 | 整条缺失 | `.-.-..`（段落） |

前两条撞码尤其误导：它让「`..-` 有 ウ/ト 两种读法」看起来像是和文モールス的
固有性质，于是解码器被设计成输出 `{う|と}` 让人二选一——**其实表里没有同码**，
那是抄错造出来的。

`{A|B}` 机制保留着：万一别处再撞码，宁可把选择权交回给人，也不要静默取一个
「语法通顺但意思全错」的答案。

### 输出是平假名

和文モールス表按惯例用**片假名**书写（無線局運用規則別表也是这样），但
解出来的日文用**平假名**更自然——歌词、台词、正文都是平假名混汉字。
所以 `dec wabun` 默认把结果转成平假名：

```bash
python3 codec.py dec wabun '-.-../..-..'            # きと
python3 codec.py dec wabun '-.-../..-..' --katakana # キト
python3 codec.py dec wabun '--.-. ..'               # じ（シ + ゛ 自动合并）
```

要对照原表核对、或谜题原文本身是片假名时，加 `--katakana` 保留片假名。

只转 `ァ–ヶ`（U+30A1–U+30F6）这一段：长音符 `ー`、浊音记号 `゛`/`゜`、
`、`、`（）` 都原样保留——整个片假名区简单减 0x60 的话，`ー` 会变成 `゜`。

为什么不能默默取第一个：`..-` 取 ト 是「じん**こと**のかみ」，
取 ウ 是「じん**こう**のかみ」（人工の神）。**两句日语都语法通顺**，
但只有后者对得上剧情。日本摩斯本身没有任何校验机制，所以「解出来了」
和「解对了」是两件事——工具宁可把候选摊开，也不替你做这个决定。

> 附带：浊音/半浊音在摩斯里是独立符号（`゛` = `..`、`゜` = `..--.`），
> 解码时会自动粘回前一个假名（`シ` + `゛` → `ジ`，输出成平假名 `じ`）。前一个
> 若恰好是 `{A|B}` 歧义组，则保持原样不硬合并。

### 一个相关的老坑

`dec morse` / `dec wabun` 的输入常常**以 `-` 开头**（`--.-.`）。早期版本的
参数解析会把「以 `-` 开头」的实参当成选项丢掉，导致整段输入消失、报
「空输入」。已修复：已知选项都在 `main()` 里消费掉了，不再按前缀过滤。


## 矩阵重排（`grid`）

很多谜题是「切块 → 排成矩阵 → 换一种读法」。`grid` 会按块宽切成矩阵，
枚举 2..12 行以及行优先/列优先/蛇形/反转等各种读法。

块数正好是完全平方数（4/9/16/25）时，转置几乎是必试项。

典型的完整链路：

```
MzIyVDMzMlQzNjM2M0EzMTJU
  ↓ base64
322T332T36363A312T
  ↓ 每 2 字符一块（base36 两位数 = 一个字节）
  ↓ 3×3 按列读
322T3A2T363133362T
  ↓ 每块 base36 → 十进制 → ASCII
nevermore
```

**块宽默认是 1，但一定要再试一次 2**——上面这个例子块宽 1 怎么转都不通。

## 六个必须知道的坑

**① ROT13 / ROT47 / Atbash 绝不能放进自动识别。**
它们对任何输入都能"成功"，且输出和输入一样可读——评分函数根本分不出来，
放进去会永远把结果带偏（早期版本就是因为这个把 `S1VWRVIg...` 解成了乱码）。
所以 `auto` 只做**有结构特征**的编码，`brute` 才把 ROT 类作为候选列出来给人工判断。

**② UTF-16 是个假中文陷阱。**
任意偶数长度的 ASCII 都能被 UTF-16BE "解码"成汉字（`aGVs...` → `慇噳扇...`），
而且全是生僻字却看起来像中文。判定办法：**用高频字比例加权**——
真中文里"的一是在不了"会大量出现，UTF-16 误读全是生僻字。脚本里已经这么做了，
自己也用这个标准人工复核。

**③ Base 系列靠"字符集 + 长度"约束，不能只看字符集。**
`helloworld` 是合法 Base64 字符集但不是合法 Base64（长度 10 不是 4 的倍数）。
Base32 看整体长度（含 padding）能不能被 8 整除；Base58 靠"排除 0OIl"这个特征；
hex 看长度能不能被 2 整除、且字符集是 `0-9a-fA-F`。

**④ 纯 0/1 位流必须整段拼起来再解，不能按行单解。**
单行 32 位只有 4 字节，而一个汉字要 3 字节——行边界几乎永远不落在字符边界上，
单行解出来必然是 `禁食�` 这种半截乱码。`dec bin` 会自动忽略换行和空格，
所以把**所有行原样一起**传进去：

```bash
python3 $C dec bin '11100111...
10100011...
...'
```

出题人通常是先写好一句话，再按固定宽度（常用 32 位）切成多行，末尾补 `00` 凑整行。
看到「11 行 × 32 位 = 44 字节 = 42 有效 + 2 填充」这种结构，直接整段当 UTF-8 位流。
反过来 `enc bin` 会输出空格分隔的单行，需要自己按固定宽度断行。
`auto` 现在对纯 0/1 输入只认 `bin`（0/1 恰好是 base64 字符集子集，以前会被 base64 抢走）；
单行给它会明确报「没有可靠的编码路径」，这是对的，别怀疑。

**⑤ UTF-32 很容易被 base16 吞掉。**
`000000230000006A00007ED9...` 这种「每码点 8 位 hex」是 **UTF-32BE**（解出 `#j给...`）。
它同时是合法 hex —— 按 base16 解会得到一串夹着 `\x00` 的乱字节，看起来像"解错了"，
实际是从一开始就选错了编码。

判别：hex 长度是 8 的倍数，**且超过一半的 8 位组带大片前导零**（`0000xxxx` 或 `xxxx0000`）。
现在 `auto` 会优先判 `utf32be`；没有 BOM 时 `dec utf32` 按首个码点的前导零分布猜字节序。

**⑥ `\xNN` 必须先聚成 bytes 再解，不能逐字节 chr()。**
`\xe4\xbd\xa0` 是「你」的 UTF-8 三字节。逐字节 `chr()` 会得到 `ä½`（latin-1 乱码）——
**它看起来像"解出来了"，但其实是错的**，比报错更危险。

正确做法：把连续的 `\xNN` 拼成 `bytes` 再 `decode('utf-8')`，失败才回退 latin-1。
`dec unicode` 现在覆盖 `\uXXXX` / `\UXXXXXXXX` / `\u{1F600}` / `U+4F60` / `%u4F60` /
以及代理对合并（`\ud83d\ude00` → 😀）。

## 顺序建议

1. `auto` 先跑一次，看它给的路径对不对
2. 不满意就 `brute`，人眼从候选里挑
3. 有明确怀疑对象再 `dec <名字>`，一次只剥一层，方便每步核对

## 盲文特别说明

`dec braille` 给英文（处理数字符号 `⠼` / 大写符号 `⠠`）；
`dec braillebits` 给**每个字符的点阵原始位串**，输出三种视图：

```json
{"per_char": [...], "bits_concat": "...", "bits_by_dot": "..."}
```

8 点盲文的点序是
```
1 4
2 5
3 6
7 8
```
如果对方用的是自定义点阵（比如 8 个固定位置的闪光点），用 `bits_by_dot`
（按点的通道竖着读）而不是 `bits_concat`（横着连起来读）。
