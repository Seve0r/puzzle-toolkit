# 编码识别的坑与解法

一串可疑文本，先别手写 `base64 -d`。判断"这属于哪种编码"比解码本身难得多，
`scripts/codec.py` 把常见格式的**结构特征**都编进去了。

```bash
C=~/.dsh/skills/codec-toolkit/scripts/codec.py

python3 $C auto 'S1VWRVIgTEFOR1VBR0U='     # 自动识别 + 递归剥皮
python3 $C brute 'aGVsbG8gd29ybGQ='        # 所有编码全试一遍，按可读性排序
python3 $C dec base58 '2NEpo7TZRRrLZSi2U'  # 指定编码解码
python3 $C grid '322T332T36363A312T'       # 矩阵重排：各种行/列/蛇形读法
python3 $C enc hex -f some.bin             # 文件输入（二进制安全）
python3 $C list                            # 看支持哪些名字
```

`auto` 会打印**解码路径**（如 `url → base64`），多层嵌套也能剥。`-q` 只输出结果。

## 支持的编码

Base16/32/32hex/58/62/64/64url/85/91、hex、二进制、十进制、八进制、
URL、HTML 实体、Unicode 转义（`\u`/`\U`/`\x`/`U+XXXX`）、Quoted-Printable、ROT13/ROT47/Atbash、
摩斯、盲文（含 8 点原始位串 `dec braillebits`）、gzip/zlib/bz2 内嵌流、
UTF-16、**UTF-32**（`utf32` 自动判字节序 / `utf32be` / `utf32le`）、GBK、
**mojibake**（乱码还原：UTF-8 被误读成 GBK，以及中日韩编码互相误读，见下方第 ⑦ 条）。

## mojibake：`浜哄彧鑳界湅` → `人只能看`

UTF-8 的中文被当成 GBK 读了一遍，是 ARG 里最常见的乱码。还原方向反直觉：
**先 `encode('gbk')` 拿回原始字节，再 `decode('utf-8')`**。

`dec mojibake` 会枚举 gb18030/gbk/big5/shift_jis/euc-kr/latin-1 等假设，
各自反编码回字节再按 UTF-8 解，**取 U+FFFD 损失率最低的那个**——
猜中时无损，猜错时字节流不合法会碎成大量替换字符。

损失率本身就是信号：

- **0%** → 数据完整，还原可信
- **>2%** → 直接报错，说明原始字节流本身就缺字节

第二种情况不能用「猜个最像的」硬输出。比如 `濡備綍杩涘叆寮備笘鐣出殑闂紵`
最好假设也损失 30.8%，还原成 `如何进入异世畳���闼�`——后半段是猜的，
当成答案会误导。**要回头找更原始的来源。**

`codec.py mojibake_rank(s)` 可以直接看到所有假设的损失率排名，用来判断数据坏在哪。

### 第二类乱码：中日韩编码互相误读

上面那套只假设「**目标是 UTF-8**」，覆盖不了另一大类：**GBK 文本被当成
Shift_JIS 读**（或反过来）。这类乱码用 UTF-8 是彻底解不出来的——字节流在
UTF-8 眼里全是非法序列，只会碎成一堆 `?`。

典型（Bilibili ARG 里真实遇到的）：

```
孨偼堦惗巹傪朰傟側偄  →  君は一生私を忘れない
```

方向是 `encode('gbk')` 拿回字节，再 `decode('shift_jis')`。

`dec mojibake` 会自动进入二级：把「源编码 × 目标编码」全组合试一遍，
判据换成**「结果是否显著更像正常文字」**（不是损失率，因为很多组合都能
0 损失但产出一堆垃圾）。命中时会打一行 `[跨编码]` 说明用了哪一对。

四个防假阳性的门槛（实测踩出来的，缺一个就乱转）：

| 门槛 | 作用 | 不设的后果 |
|---|---|---|
| 原文以 **CJK 汉字**为主（≥50%） | GB18030 是全 Unicode 覆盖，任何文本都能被它编回字节 | 俄文 `Русский текст` 被"翻译"成 `妓批扼扼抗我抄` |
| 结果可读度 **≥0.85** | 挡住私用区/控制符/生僻字 | `锟斤拷` 被解成韩文 `占쏙옙` |
| 可读度**提升 ≥0.4** | 已经是正常文字的不再改 | 正常中文被反复误转 |
| 长度 **≥3** | 单字字节碰巧合法 | `茻` → `踈` |

「可读度」= 汉字看是否 GB2312 或 Shift_JIS 收录（日文新字体 `実`/`嘘`
在 GB2312 里没有，只看 GB2312 会把它们当成乱码特征），假名算好，
半角片假名、私用区、控制符算坏。

### 已知编码对就直接指定：`--from` / `--to`

自动认不出、或你已知作者用的编码时，别让它猜：

```bash
python3 codec.py dec mojibake --from gbk --to shift_jis '孨偼堦惗巹傪朰傟側偄'
# 君は一生私を忘れない
```

含义是「这段文字原本是按 `<源>` 编成字节的，被当 `<目标>` 解了」。只给一侧
时另一侧取默认（源 `gb18030`、目标 `utf-8`），并在 stderr 说清用了默认值。
这条路不做任何猜测，结果可复现。

### 单字/双字不要用 `dec mojibake`

一两个字符不足以下结论，字节碰巧合法就会给出误导性结果（`茻` → `踈`、
`あいうえお` → `ƦƨƪƬƮ`）。工具现在会直接拒绝短于 3 字符的输入——
真实的乱码是被系统性误读的产物，必然成串出现。

### 数据半路丢了字节：`�` 分段还原

谜题数据常常不是编码错位，而是**真丢了几个字节**——从网页复制、OCR、
聊天记录转存都会这样，缺失处变成 `�`（U+FFFD）。

这种输入以前是死路：U+FFFD 不在任何编码里，整段 `encode()` 直接抛异常，
所有假设被跳过，工具只能说「数据损坏」。**但缺失处两侧的字节是完好的**，
切段分别还原就能把能救的全救回来：

```
输入：崱傑偱慡偰� 偺壧偲夋柺偼堄枴偑偁� 傞丅恀幚偑柧傜偐偵…
输出：今まで全て� の歌と画面は意味があ� る。真実が明らかにな…
--best：今まで全て? の歌と画面は意味があ? る。真実が明らかにな…
```

`--best` 会把 `�` 显示成 `?`（更好读）。工具会报告「原文 N 处字节缺失、
成功还原 M/M 段」。

- **编码对统一**：取「能把最多段解成正常文字」的那一对，而不是逐段各自猜——
  同一段乱码本来自同一对编码，逐段独立猜会拼出互相矛盾的版本。
- **准入门槛**：原文得「像中日韩乱码」（CJK 汉字占多数）而**不是本来就正常**。
  不设这条的话，`正常中文�乱码` 会被转成 `攣끽櫓匡�쫘쯤`、`今まで全て� の歌`
  会被转成 `書まで畠て� の梧`——分段后每段只有两三个字，假阳性特别容易。
- `--from gbk --to shift_jis` 遇到 `�` 也会自动分段，不会因为编不回去而失败。

### `€` 与私用区字符：乱码里的「半个字节」

UTF-8 中文 3 字节、GBK 汉字 2 字节，两者不对齐，所以乱码里经常出现**孤立的
半个字节**。这类字节在 CP936 里是这么表示的：

| 原字节 | 乱码里看到的字符 | 说明 |
|---|---|---|
| `0x80` | `€`（U+20AC） | CP936 把单字节 0x80 定义成欧元符号 |
| 用户自定义区双字节 | U+E000–U+F8FF 私用区字符 | 如 `\ue043` 对应字节 `AA E4` |

私用区字符交给 `encode('gb18030')` 能正确还原成原始字节，**但 `€` 不行**：
`gb18030` 把 U+20AC 编成双字节 `A2E3`，凭空多出一个字节，导致它之后的内容
整行错位一格。所以 GBK 系回编码必须手动把 `€` 还原成 `0x80`（代码里是
`_encode_back()`）。

不处理时症状很典型：本来能无损还原的一行，解出来是「居民为什么不购入
**丢?个**亲生孩子」——正确的「一个」被吃掉，损失率还被抬到 5.3%，
反而把正确假设挤掉了。

### 多层乱码：`--deep`

乱码可能套了好几层。`--deep [N]` 会反复还原，直到「正常文字占比」达到 N%
（0~100，默认 50）：

```bash
python3 codec.py dec mojibake --deep -f 原文.txt      # 默认阈值 50
python3 codec.py dec mojibake --deep 85 -f 原文.txt   # 解得更彻底
```

它逐层打印损失率和可读率，标出采信第几层。「正常文字占比」= 汉字看是否
GB2312 常用、假名算正常（ASCII 不算，否则解过头的 ASCII 噪音会被算成高可读率）。

跨编码那一级也会参与，所以 `--deep` 对 `孨偼堦惗巹傪朰傟側偄` 这类同样一步到位。

**可读率不是单调的**：一串双层乱码实测是 33.7% → 36.4% → 88.5% → 0%，
所以取的是全局最高那层而不是最后那层，解过头会自动退回。

**局限**：只对「整段层数一致」的乱码有效。如果同一行里有的部分已经解开、
有的还没有（混合层数），自动递归会把已解好的部分重新弄坏——这种情况必须
手工切段，分别用 `--best` 处理。


## Punycode：`XN--L8JEXE7NOG3971A` → `あの子がきらい`

把非 ASCII 文本塞进纯 ASCII 域名的编码，IDN（`.jp` 的日文域名那种）就用它。
固定带 `xn--` 前缀，属于**可逆编码**，性质接近 Base64 而不是加密。

```bash
python3 codec.py dec punycode 'XN--L8JEXE7NOG3971A'   # あの子がきらい
python3 codec.py dec punycode -f 四条.txt              # 多行批量，一段一行输出
python3 codec.py enc punycode 'あの子がきらい'          # xn--l8jexe7nog3971a
```

`auto` 会自动认出 `xn--` 前缀。

**两个坑**：

1. **不能用 `idna` codec 解**。`idna` 会当成完整域名做校验，谜题数据里带逗号
   （例如 `XN--,-47TL2MZE6MYDZA3P` 解出 `おはよう,ニセモノ`）或空格就一律报错。
   必须剥掉前缀后直接走 `punycode` codec。
2. **必须抢在 base64url 前面**。这类串长度常是 4 的倍数、字符集又落在
   base64url 里（`-` 是合法字符），不优先识别就会被 base64url 抢走，解出乱码。

实测样例（ERIKO #003）：

| Punycode | 明文 |
|---|---|
| `XN--L8JEXE7NOG3971A` | あの子がきらい |
| `XN--,-47TL2MZE6MYDZA3P` | おはよう,ニセモノ |
| `XN--N8JPD2B0B8RJB` | わたしがきらい |
| `XN--68JP3C3G5ILDWA3N` | わたしはニセモノ |


## 和文モールス（`dec wabun`）

日文假名用的摩斯体系（和文モールス符号 / Wabun code），**和国际摩斯是两套
完全不同的表**：同一个符号在两边代表不同字符。`....` 在国际是 `H`，
在和文是 `ヌ`。所以必须显式指定用哪套：

```bash
python3 codec.py dec wabun '--.-./../.-.-./----/..-/..--/'   # 和文
python3 codec.py dec morse '.... . .-.. .-.. ---'             # 国际
```

`auto` 会自动分辨：**只要有一段码在国际表里查不到，就判定为和文**
（`--.-.` 这种国际根本没有）；全部能按国际解释时优先国际。

### ★ 同码问题：不会替你选

和文表里有同一个符号对应多个假名的情况：

| 符号 | 可能 |
|---|---|
| `..-` | ウ / ト |
| `-.--.` | ル / 「（」 |

这类位置**解码结果里会用 `{A|B}` 标出来**，把选择交回给你：

```
$ codec.py dec wabun '--.-./../.-.-./----/..-/..--/.-../..-.-/...'
ジンコ{ウ|ト}ノカミニ…
```

为什么不能默默取第一个：`..-` 取 ト 是「じん**こと**のかみ」，
取 ウ 是「じん**こう**のかみ」（人工の神）。**两句日语都语法通顺**，
但只有后者对得上剧情。日本摩斯本身没有任何校验机制，所以「解出来了」
和「解对了」是两件事——工具宁可把候选摊开，也不替你做这个决定。

> 附带：浊音/半浊音在摩斯里是独立符号（`゛` = `..`、`゜` = `..--.`），
> 解码时会自动粘回前一个假名（`シ` + `゛` → `ジ`）。前一个若恰好是
> `{A|B}` 歧义组，则保持原样不硬合并。

### 一个相关的老坑

`dec morse` / `dec wabun` 的输入常常**以 `-` 开头**（`--.-.`）。早期版本的
参数解析会把「以 `-` 开头」的实参当成选项丢掉，导致整段输入消失、报
「空输入」。已修复：已知选项都在 `main()` 里消费掉了，不再按前缀过滤。


## 矩阵重排（`grid`）

很多谜题是「切块 → 排成矩阵 → 换一种读法」。`grid` 会按块宽切成矩阵，
枚举 2..12 行以及行优先/列优先/蛇形/反转等各种读法。

块数正好是完全平方数（4/9/16/25）时，转置几乎是必试项。

典型的完整链路：

```
MzIyVDMzMlQzNjM2M0EzMTJU
  ↓ base64
322T332T36363A312T
  ↓ 每 2 字符一块（base36 两位数 = 一个字节）
  ↓ 3×3 按列读
322T3A2T363133362T
  ↓ 每块 base36 → 十进制 → ASCII
nevermore
```

**块宽默认是 1，但一定要再试一次 2**——上面这个例子块宽 1 怎么转都不通。

## 六个必须知道的坑

**① ROT13 / ROT47 / Atbash 绝不能放进自动识别。**
它们对任何输入都能"成功"，且输出和输入一样可读——评分函数根本分不出来，
放进去会永远把结果带偏（早期版本就是因为这个把 `S1VWRVIg...` 解成了乱码）。
所以 `auto` 只做**有结构特征**的编码，`brute` 才把 ROT 类作为候选列出来给人工判断。

**② UTF-16 是个假中文陷阱。**
任意偶数长度的 ASCII 都能被 UTF-16BE "解码"成汉字（`aGVs...` → `慇噳扇...`），
而且全是生僻字却看起来像中文。判定办法：**用高频字比例加权**——
真中文里"的一是在不了"会大量出现，UTF-16 误读全是生僻字。脚本里已经这么做了，
自己也用这个标准人工复核。

**③ Base 系列靠"字符集 + 长度"约束，不能只看字符集。**
`helloworld` 是合法 Base64 字符集但不是合法 Base64（长度 10 不是 4 的倍数）。
Base32 看整体长度（含 padding）能不能被 8 整除；Base58 靠"排除 0OIl"这个特征；
hex 看长度能不能被 2 整除、且字符集是 `0-9a-fA-F`。

**④ 纯 0/1 位流必须整段拼起来再解，不能按行单解。**
单行 32 位只有 4 字节，而一个汉字要 3 字节——行边界几乎永远不落在字符边界上，
单行解出来必然是 `禁食�` 这种半截乱码。`dec bin` 会自动忽略换行和空格，
所以把**所有行原样一起**传进去：

```bash
python3 $C dec bin '11100111...
10100011...
...'
```

出题人通常是先写好一句话，再按固定宽度（常用 32 位）切成多行，末尾补 `00` 凑整行。
看到「11 行 × 32 位 = 44 字节 = 42 有效 + 2 填充」这种结构，直接整段当 UTF-8 位流。
反过来 `enc bin` 会输出空格分隔的单行，需要自己按固定宽度断行。
`auto` 现在对纯 0/1 输入只认 `bin`（0/1 恰好是 base64 字符集子集，以前会被 base64 抢走）；
单行给它会明确报「没有可靠的编码路径」，这是对的，别怀疑。

**⑤ UTF-32 很容易被 base16 吞掉。**
`000000230000006A00007ED9...` 这种「每码点 8 位 hex」是 **UTF-32BE**（解出 `#j给...`）。
它同时是合法 hex —— 按 base16 解会得到一串夹着 `\x00` 的乱字节，看起来像"解错了"，
实际是从一开始就选错了编码。

判别：hex 长度是 8 的倍数，**且超过一半的 8 位组带大片前导零**（`0000xxxx` 或 `xxxx0000`）。
现在 `auto` 会优先判 `utf32be`；没有 BOM 时 `dec utf32` 按首个码点的前导零分布猜字节序。

**⑥ `\xNN` 必须先聚成 bytes 再解，不能逐字节 chr()。**
`\xe4\xbd\xa0` 是「你」的 UTF-8 三字节。逐字节 `chr()` 会得到 `ä½`（latin-1 乱码）——
**它看起来像"解出来了"，但其实是错的**，比报错更危险。

正确做法：把连续的 `\xNN` 拼成 `bytes` 再 `decode('utf-8')`，失败才回退 latin-1。
`dec unicode` 现在覆盖 `\uXXXX` / `\UXXXXXXXX` / `\u{1F600}` / `U+4F60` / `%u4F60` /
以及代理对合并（`\ud83d\ude00` → 😀）。

## 顺序建议

1. `auto` 先跑一次，看它给的路径对不对
2. 不满意就 `brute`，人眼从候选里挑
3. 有明确怀疑对象再 `dec <名字>`，一次只剥一层，方便每步核对

## 盲文特别说明

`dec braille` 给英文（处理数字符号 `⠼` / 大写符号 `⠠`）；
`dec braillebits` 给**每个字符的点阵原始位串**，输出三种视图：

```json
{"per_char": [...], "bits_concat": "...", "bits_by_dot": "..."}
```

8 点盲文的点序是
```
1 4
2 5
3 6
7 8
```
如果对方用的是自定义点阵（比如 8 个固定位置的闪光点），用 `bits_by_dot`
（按点的通道竖着读）而不是 `bits_concat`（横着连起来读）。
