# 进制转换

```bash
N=~/.dsh/skills/num-toolkit/scripts/num.py
python3 $N <数> ...
```

| 写法 | 结果 |
|---|---|
| `num.py 255` | `dec 255` / `hex ff` / `bin 11111111` / `oct 377` |
| `num.py 255 --to 16` | `ff` |
| `num.py ff --from 16` | `255` |
| `num.py 0b1010` | `10`（认 `0x`/`0b`/`0o` 前缀） |
| `num.py 255 --to 16 --upper` | `FF` |
| `num.py 255 --to 16 --prefix` | `0xff` |
| `num.py 5 --to 2 --pad 8` | `00000101` |
| `num.py 1 2 3 --to 2 --pad 8` | 三行，各 8 位 |
| `num.py -f nums.txt --to 16` | 批量（每行一个，行内空格分隔算多个） |
| `cat n.txt \| num.py --to 16` | 管道；不给数就读 stdin |
| `num.py zz --from 36` | `1295`（2..36 全支持） |

`--from` / `--to` 都是 **2..36**。不给 `--to` 就列出 dec/hex/bin/oct 四种形式。

## 三条要点

**① 这是「数值视角」，不是「字节流视角」。**

| 你想要的 | 用哪个 |
|---|---|
| 一个数换种写法（`ff` ↔ 255） | `num.py` |
| 字节序列 ↔ 文本（`48656c6c6f` ↔ `Hello`） | `codec.py dec hex` |

`codec.py` 里的 hex/bin/dec 全是「字节流编解码」：`enc hex "Hi"` → `4869`，
`enc hex 255` → `323535`（把 "255" 当文本，每个字符转 hex）。它做不到
「255 → ff」，这是两个工具的分界线。

**② `--pad` 不是美化，是保信息。**

进制转换会吃掉前导零：`0x00ff` 和 `0xff` 是同一个数，但在数据里是两种字节。

```bash
python3 -c "print(bin(int('00000001',2)))"   # 0b1 —— 8 位变 1 位
```

做点阵位流、定长哈希字段的往返时**必须**补零：

```bash
num.py 1 2 3 --to 2 --pad 8     # 00000001 / 00000010 / 00000011
```

**③ 进制上限是 36，这是符号的物理上限。**

`0-9` + `a-z` 正好 36 个。再往上要自带字符集（base58/62/64 就是这么来的），
那属于**编码**不属于进制，用 `codec.py`。脚本对 `--from 37` 会直接报错并提示。

## 陷阱

- **不给 `--from` 时，纯数字一律按十进制。** `01101001` 会被读成 `1101001`。
  脚本发现「纯 0/1 且长度是 8 的倍数」时会往 stderr 提一句，但**不会替你改判定**
  ——进制猜错的代价比多敲一个 `--from 2` 高得多。
- 含 `a-f` 的判十六进制；`0x` / `0b` / `0o` 前缀优先于一切自动判定。
- `-f` 不能和位置参数同时给（会报错，避免"到底转哪个"的歧义）。
- 负数照常支持：`num.py -255 --to 16` → `-ff`；补零时为 `-0005` 形式（符号不算在
  `--pad` 的位数里）。
- 大整数直接吃，Python 的 `int` 没有位宽上限（RSA 的 `n` 转 hex 是常见用法）。

## 判据

- 转完之后用 `--from` 反向转一次能回到原值 → 没丢信息
- 补零后的字符数 == `--pad` 的值（正负号、`0x` 前缀不算）
- 和 Python 内置对得上：`--to 16` 应等于 `format(n,"x")`

证据：puzzle-toolkit `num.py`，2000 次随机往返（含 128 位大数）+ 1500 次与
`format(n,"x"/"b"/"o"/"d")` 对比，全部一致
